# Expunge Evaluation Against the Hackathon Resource Guide

Evaluated 11 October 2026 against the linked native Google Doc, tab t.0, read directly through Google Drive: [Harness Engineering and Model Wrangling Hackathon Resource Guide](https://docs.google.com/document/d/1iMfdEg304T1r25RRRhJW3hDTjjYlSNnEpYj2qXA2CLo). The existing implementation blueprint remains unchanged. This is an assessment of the proposed design; no application behavior has been built or verified.

## Verdict

**Expunge is a strong fit for Statement One, Recursive Harnessing.** It changes the environment around a fixed model: selected context, discovery/workflow graph, guardrail predicates and tool prerequisites. MongoDB owns the actual data, durable learning state and tested-version authority. The domain provides a concrete outcome that can be independently checked.

The two most consequential risks are showing meaningful autonomous architectural adaptation and distinguishing original event work from the three existing applications. The architecture should stay at full scope; the presentation and evidence should make the original learning mechanism easy to assess.

## The central demonstration test

A new lesson string or green status badge is weak evidence. Show a generated change that alters what executes: for example, the workflow begins inspecting nested/reference structures, introduces a verification branch, or makes completion require a valid receipt. Display the artifact diff and actual tool sequence before and after.

Then use a new subject in a withheld structural composition. It must clean the intended records, preserve unrelated data and report coverage truthfully. The model, evaluator and scope remain fixed. Include an expert-static comparison so a rediscovered obvious procedure is not presented as unprecedented intelligence.

The guide does not demand unbounded code invention, weight training or a mathematically proven recursive acceleration. A bounded typed harness that automatically selects/composes executable policies can fit Statement One. The stronger meta-improver experiment is additional evidence and remains in the full blueprint; its result must be measured independently.

## Position Statement Two accurately

Expunge's checkpoints, resumable jobs and cross-run memory are useful long-running infrastructure. They do not demonstrate a single session sustaining billion-token context or comparable duration. Submit principally under Statement One. The guide requires at least one statement, so this does not weaken that eligibility claim. Preserve the durable-execution functionality without overstating what it proves.

## Originality and reuse

The guide supplies starter-code and showcase resources, which makes a blanket claim that all framework reuse is banned unsupported. It also does not explicitly authorize submitting a lightly modified complete pre-existing application.

OpenDots' UI/auth/workspace, OpenBot's computer services and OpenMuse's helper code are attributed foundations. The new contribution is Expunge's schema-aware cleanup, fixed verifier, evidence-driven four-surface evolution, Atlas authority/receipts, adversarial curriculum and measured optimizer comparison. Center the submission on that work. A full-fork eligibility ruling remains separate from legal licensing; this evaluation neither invents approval nor declares an automatic disqualification.

## Raindrop evidence

The guide describes finding wrong answers, frustrated users and broken tools. Expunge naturally supplies a wrong-success episode: the worker says cleanup succeeded while a legitimate copy remains. Actual remote tool/model evidence should inform diagnosis; tracing the improver also fits the monitoring purpose.

If our verifier discovers the failure and uploads feedback, label it verifier feedback. If a vendor classifier detects a signal, identify that source. A score echoed through the service is real instrumentation but weak evidence of using its observation capabilities. Use the existing score-only/wrong-incident controls and actual remote evidence chain.

## Presentation and submission adjustments

Keep the complete implementation scope. For the one-minute video, use one incident: initial miss; real trace and generated architectural diff; admission with a protected case; newly pinned run; actual MongoDB receipt. Put role matrices, privacy lineage, recovery, Hider and meta-campaign details in the repository and expanded demo/Q&A evidence.

Before implementation, add explicit sandbox identity and development Agent Skills/MCP/query-guide checks to the coordinator's kickoff manifest. Before submission, verify public access, on-site recording, presence, original-work inventory and the exact deployed artifact/data/model hashes. These are concrete acceptance items, not additional compulsory product features.

## What this particular document does not establish

It contains no numeric judging weights, dashboard prohibition, detailed live-demo duration or Raindrop RSI prize criteria. Earlier research may discuss those from other sources; they cannot be attributed to this resource guide. The guide's resource lists also do not make every MongoDB feature, Atlas Agent Engine, Modelence, Kiro, Cursor or ElevenLabs compulsory.
