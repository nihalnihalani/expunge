# Synthetic fixtures

This package is for trusted development, fixture creation and evaluation services. All subjects, emails, payloads and business values are generated synthetics; email domains are `example.invalid`. There is no customer-data input. Worlds contain six collections and at most 500 documents (the uniform recipe currently generates at most 498), with five reference hops at most.

`createWorldSpec({family, seed, ...options})` creates a recipe-only `WorldSpec`. `generateWorld(spec, seed, binding?: ScopeKey)` returns the visible world. A supplied binding must come from trusted server configuration/authentication, never model arguments.

ScopeKey handling (frozen interface 3): `resolveScopeKey` selects exactly `{tenantId, env, scopeId}`. Extra `ActorContext` keys (`actorId`, `authorizationRevision`, anything else) never reach a hash, a document or the registry. Identifier values are opaque and never trimmed, case-folded or normalized; an unusable binding is a `trusted_scope_binding` quarantine, not a guess. There is ONE default binding, `DEFAULT_SCOPE_KEY` (`synthetic-evaluation-tenant` / `evaluation` / `synthetic-evaluation-scope`), used both for world hashing and for the emitted registry scope, so the implicit default and its explicit equivalent have identical `worldId` and `scopeId`. Registry rows are keyed by ScopeKey, so worlds seeded side by side need distinct scopes: `deriveWorldScopeKey(spec, seed, base?)` gives each world instance its own `scopeId`; it is for the trusted fixture builder, driven by configuration, never by model, client or Hider arguments. Final split builders use the evaluation default.

Instance isolation: every record `_id`, identity token and alias is derived from the world instance (`worldId = H(specHash, seed, ScopeKey)`), because MongoDB `_id` uniqueness is collection-wide. The same seed under two tenants, environments or scopes gives disjoint IDs and identity values; a reset of the same `(spec, seed, scope)` reproduces identical IDs; the structural recipe is isomorphic across instances. The independent oracle derives the same IDs through its own formula, and tests prove every manifest address and preservation path resolves to a real document.

Record shape is not an answer channel. Each collection holds one record per chain: chain 0 is the subject's, every other chain is a decoy built by the same recipe from its own identity tokens and wired to other decoys of its own chain (including mixed arrays, null identity patterns, duplicate and cross-collection references). Record IDs are opaque (`syn_<24 hex>`), display names use one format (`Synthetic <Word> <Word>`) and only the subject's namesake chains share the subject's name. `shape.ts` (trusted) runs four shape-only detectors, including a port of the DA-1 outlier rule and generic field-presence/array-length/format fingerprints; reference admission quarantines a world with reason `shape_leak` when any detector beats the target fraction among candidates by more than `SHAPE_PRECISION_TOLERANCE` (0.02). Display-name collision with the intended namesakes is deliberately kept: it narrows the candidates to the namesake group only.

Visible records use string BSON IDs and `{_id, tenantId, env, worldId, _rev, data, eligibility, access, lifecycle}`. The scope registry declares safe field paths with `*` for array traversal, reference-field joins, allowed effects and fixed owner policy. Visible `schema.referenceExpansion` distinguishes incoming ownership references from outgoing references in the reverse family. Reference edges are constructed from layouts and visible source records. No oracle target, expectation or preservation hash enters them. Creation order and business ordinals are randomized independently of target status.

Families cover direct/nested identity, arrays, exact aliases, account/event composition, duplicates/cycles, disconnected namesakes, mixed eligibility, interrupted/lost-acknowledgement retries, reverse traversal, diamond joins and archive bridges. Display-name equality never authorizes an effect. Redaction changes exact subject/reference bindings and the private payload; restriction retains record bytes under restricted access; tombstones remove exact bindings/payload and retain unrelated business metadata. These are owner policy effects, not legal compliance guarantees.

The root export contains visible fixture APIs and types. `@expunge/fixtures/sealed` is privileged: `generateSealedFixture(spec, seed, binding?, observation?)` additionally builds a hidden manifest from an independent intent recipe; `buildSealedSplitPlan(masterSeed)` returns private seeds/specs. The oracle does not invoke the reference solver or its discovery algorithm. It freezes exact expected poststates, untouched-record hashes and protected field hashes, plus an independent trusted ScopeKey/revision, registry/schema hashes and subject handle. `assertManifestIntegrity` rejects altered manifests. Keep fixture packages, seed material and manifests out of worker/candidate images, tools, logs and telemetry; TypeScript-only `import type` usage erases at runtime. Packaging/access-denial checks remain an integration responsibility, not something unit tests alone establish.

The optional `TrustedObservationRecipe={omitFieldIds,limitations}` is a trusted fixture/observer construction input, separate from WorldSpec. It removes those observed descriptors/reference declarations, increments scope revision, records explicit limitations and seals the resulting registry before execution. The independent expected targets remain unchanged. Customer identity/root fields and record IDs cannot be omitted. This supports honest partial-known-scope trials; editing scope/schema metadata after sealing fails grading rather than manufacturing a scoped-success case.

Recipe paths follow the shared `@expunge/contracts` grammar (`isFieldPath`: identifier segments or one `*`, never first, 1..16 segments) with a fixture-specific tighter bound of 6 segments (`RECIPE_PATH_MAX_SEGMENTS`) so a registry path, which adds a leading `data`, stays well inside the shared bound. Registry descriptors may also name the record key `_id` (`isRegistryFieldPath`). Leading wildcards, non-string segments, unsafe names and overlapping paths are rejected; tests check that every path emitted by every family and split registry passes the shared grammar, and that assignment and traversal agree for each supported shape.

`buildSealedSplitPlan(masterSeed)` requires a high-entropy master seed (at least 256 bits of lowercase hex) and throws `InvalidMasterSeed` otherwise: every held-out seed, target ID and held-out field name derives from it. `publicSplitCommitment(plan)` strips seeds/specs and commits 2 training, 8 protected, 8 validation and 24 final structural worlds. Protected twins preserve the known structures with additional namesakes. Validation and final worlds use separate field compositions whose segment names are derived from each entry's private seed (no held-out path vocabulary is listed in source), and withheld topology families. The public per-entry `structuralHash` is salted with the entry's private seed, so structures cannot be recovered by enumerating the small recipe space; revealing the seeds after final scoring lets an auditor recompute it. IDs alone are not holdouts. Freeze this commitment before evolution and never select a version on final results. The held-out family names are documented and therefore public; the held-out instances (seeds, paths, IDs) are not.

Generator and split-builder commitments hash actual source bytes under stable relative module labels, including `packages/contracts/src/index.ts` (so a contracts edit changes the generator commitment: recompute after contracts settle). They are checkout-path independent and change when code changes. This source-export workspace intentionally ships TypeScript to the trusted service; a later compiled deployment must freeze its compiled artifacts and retain/verify corresponding source commitments.

Sources followed: `docs/expunge/CONTRACTS.md` (WorldSpec, ScopeRegistry, fixed truth), `DATA-MODEL.md` (private database/principal boundary), `SOURCE-MAP.md` and `ACCEPTANCE.md` (structural holdouts and reference admission). The generator/reference/evaluator are new application code and copy no vendor API implementation.

Verification: `npx vitest run packages/fixtures/test packages/grader/test`; `npx tsc --noEmit`; `npx eslint packages/fixtures packages/grader`; `npx prettier --check packages/fixtures packages/grader`. Tests include explicit hand-checked restriction/tombstone/delete outcomes, ScopeKey/instance isolation, shared-grammar and bounds checks, and shape-only adversary canaries for every family and split, not only comparisons to generated expectations. No Atlas or provider proof is claimed by these commands.
